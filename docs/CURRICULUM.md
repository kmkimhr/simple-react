# React 학습 커리큘럼 — 프로젝트 "Taskly"

하나의 앱을 12단계에 걸쳐 키워나가면서 React를 배웁니다.
매 단계는 **"이 기능을 만들려면 이 개념이 필요하다"** 순서로 배치했습니다.
개념을 먼저 외우고 나중에 쓰는 게 아니라, 막히는 지점에서 개념이 등장합니다.

- **언어**: TypeScript (처음부터)
- **빌드 도구**: Vite
- **React 버전**: 19
- **스타일링**: 순수 CSS + CSS Modules
- **진행 방식**: 각 단계의 레슨 문서(`docs/lessons/NN-*.md`)에 있는 코드를 직접 손으로 옮겨 적습니다.

문서 끝에 [부록 A. 훅 지도](#부록-a-훅-지도)와 [부록 B. 상태의 네 가지 거처](#부록-b-상태의-네-가지-거처)가 있습니다. 진행하다 길을 잃으면 거기로 돌아오세요.

## 단계별 상세

### 0단계 — 환경 세팅
**목표**: `npm run dev`로 브라우저에 내 화면이 뜬다.

- Node / npm 이 무엇이고 왜 필요한지
- Vite로 React + TypeScript 프로젝트 생성
- `package.json`, `src/main.tsx`, `index.html`이 어떻게 연결되는지
- `createRoot(document.getElementById('root')!).render(...)` 한 줄이 하는 일
- 생성된 기본 코드 중 지워도 되는 것 정리
- TS 설정 파일(`tsconfig.json`, `tsconfig.node.json`)이 왜 두 개인지 — 지금은 "브라우저용 / 빌드도구용"까지만
- **`<StrictMode>`가 뭔지 지금 봐 두기**
  - `main.tsx`를 감싸고 있는 그 태그. **개발 모드에서만** 컴포넌트를 두 번 렌더하고 Effect를 두 번 실행한다
  - 버그가 아니라 **일부러** 그러는 것 — 부작용이 잘못 든 코드를 일찍 잡아내려고
  - 프로덕션 빌드에서는 한 번만 실행된다
  - 4단계에서 이것 때문에 반드시 한 번 놀라게 됩니다. 그때 다시 옵니다

✅ **체크포인트**: `index.html` → `main.tsx` → `App.tsx`로 이어지는 흐름을 말로 설명할 수 있다.

### 1단계 — 컴포넌트와 props
**목표**: 하드코딩된 할 일 3개가 화면에 리스트로 보인다.

- JSX는 HTML이 아니다 (`className`, `{}` 표현식, 하나의 부모 요소)
- 부모 요소가 필요하지만 `<div>`를 늘리기 싫을 때 — **Fragment** (`<>...</>`)
- 컴포넌트 = 함수, 반환값 = 화면
- props로 데이터 내려주기, TypeScript로 props 타입 정의하기
  - `type` vs `interface` — 지금은 `type`으로 통일하고 이유는 나중에
  - 선택적 prop(`?`), 기본값, 유니온 타입으로 제한하기 (`variant: 'primary' | 'ghost'`)
- 배열 `.map()`으로 리스트 렌더링
- **컴포넌트는 순수해야 한다**
  - 같은 props가 들어오면 항상 같은 결과가 나와야 한다
  - 렌더링 중에 바깥 변수를 바꾸거나, `Math.random()` / `Date.now()`를 쓰거나, DOM을 만지지 않는다
  - 이 규칙을 어기면 0단계의 StrictMode 이중 렌더에서 바로 티가 난다
- **props는 읽기 전용** — 자식이 받은 props를 직접 수정하지 않는다
- 파일 분리: `TodoList` / `TodoItem`

✅ **체크포인트**: props를 하나 추가해서 아이템에 새 정보를 표시할 수 있다.

### 2단계 — 상태와 이벤트
**목표**: 할 일을 추가하고, 체크하고, 지울 수 있다.

#### 2-A. 상태의 기본

- `useState`: 화면이 바뀌어야 하는 값은 상태다
- 이벤트 핸들러 (`onClick`, `onChange`) 와 **함수 전달 vs 호출**의 차이
  - `onClick={handleClick}` vs `onClick={handleClick()}` vs `onClick={() => handleClick(id)}`
- 이벤트 객체: `e.preventDefault()`, `e.stopPropagation()`
- 조건부 렌더링: 빈 목록일 때 안내 문구 (`&&`, 삼항, early return)
  - `&&`의 함정 — `{items.length && <List/>}`는 0을 화면에 찍는다

#### 2-B. 상태를 바꾸는 올바른 방법

- **상태는 직접 수정하지 않는다** — 불변성, 스프레드 연산자
- 배열 불변 업데이트 4종 세트
  - 추가 `[...todos, next]` / 삭제 `todos.filter(...)` / 수정 `todos.map(...)` / 정렬은 복사 후 `[...todos].sort(...)`
  - 쓰면 안 되는 것: `push`, `splice`, `sort`, `reverse` (원본을 바꾼다)
- 객체 안의 객체를 바꿀 때 — 바깥부터 안까지 전부 새로 만들어야 하는 이유
- **함수형 업데이트** `setCount(c => c + 1)`
  - 같은 핸들러에서 `setCount(count + 1)`을 두 번 부르면 왜 1만 오르는가
  - React는 상태 변경을 **모아서 한 번에 처리한다**(batching). `count`는 그 렌더 시점에 찍힌 값이다
  - 이전 값에 기대는 업데이트는 **항상** 함수형으로

#### 2-C. `key`와 상태의 정체성

- 리스트의 `key`가 왜 필요한지, **index를 쓰면 안 되는 이유**
- 한 걸음 더 — **React는 컴포넌트의 상태를 "트리에서의 위치"로 기억한다**
  - 같은 자리에 같은 컴포넌트가 있으면 상태가 유지된다
  - 자리가 바뀌거나 `key`가 바뀌면 **상태가 초기화된다**
  - 이걸 역이용하면 `<EditForm key={todo.id} />`처럼 **`key`로 폼을 강제로 리셋**할 수 있다
  - 6단계에서 "상세 페이지를 옮겼는데 이전 내용이 남아 있다" 문제를 이걸로 해결합니다

✅ **체크포인트 2-A**: "상태를 바꿨는데 화면이 안 바뀐다"는 상황의 원인을 짚을 수 있다.
✅ **체크포인트 2-B**: 버튼 한 번에 카운터를 2 올리는 코드를 함수형 업데이트로 고칠 수 있다.

### 3단계 — 폼과 상태 설계
**목표**: 전체 / 진행중 / 완료 필터와 검색이 동작한다.

#### 3-A. 폼 다루기

- 제어 컴포넌트(controlled input) — 입력값도 상태다
- 비제어 컴포넌트는 언제 쓰는지 (4단계 `useRef` 이후 다시 언급)
- form 제출, `preventDefault`, 입력 검증
- **`useId`** — `label`의 `htmlFor`와 `input`의 `id` 연결
  - 컴포넌트를 여러 번 렌더해도 id가 겹치지 않게 해준다. 직접 카운터를 돌리면 안 되는 이유
- 여러 입력을 한 객체 상태로 묶고 `name` 속성으로 한 핸들러에서 처리하기

#### 3-B. 상태 설계 — 이 단계의 진짜 주제

- 상태 끌어올리기(lifting state up): 두 컴포넌트가 같은 값을 볼 때
- **파생 상태를 만들지 마라** — 필터링 결과는 상태가 아니라 계산이다
  - `filteredTodos`를 `useState`로 두면 `todos`가 바뀔 때마다 손으로 동기화해야 한다. 그 동기화는 반드시 언젠가 빠진다
- **좋은 상태 구조의 원칙 4가지**
  1. **중복 금지** — 같은 값을 두 군데 두지 않는다 (`todos`와 `selectedTodo` 객체를 함께 두지 말고 `selectedId`만 둔다)
  2. **모순 금지** — `isLoading`과 `isError`를 따로 두면 둘 다 `true`인 상태가 만들어진다. `status: 'idle' | 'loading' | 'success' | 'error'` 하나로
  3. **관련된 것은 묶기** — 항상 같이 바뀌는 값은 한 객체로
  4. **깊은 중첩 피하기** — 3단 이상 중첩되면 평평하게(정규화) 펴는 걸 고민한다
- 계산으로 뽑을 수 있으면 상태로 두지 않는다 — `todos.filter(t => !t.done).length`

#### 3-C. 상태가 복잡해지면 `useReducer`

- `useState`가 5~6개로 늘고 서로 얽히기 시작하는 지점에서 도입
- action 타입을 TS **구별된 유니온**(discriminated union)으로 정의하기
  - `type Action = { type: 'add'; text: string } | { type: 'toggle'; id: string }`
  - `switch (action.type)` 안에서 타입이 자동으로 좁혀지는 걸 확인
- reducer는 **순수 함수** — 1단계의 순수성 규칙이 여기서 다시 나온다
- 중첩 객체 업데이트가 아파지면 **Immer**(`useImmerReducer`)
  - `draft.todos[0].done = true`처럼 쓰지만 실제로는 새 객체가 나온다
  - 편해 보여도 먼저 손으로 스프레드를 써 보고 나서 도입할 것

#### 3-D. React 19의 form action (맛보기)

- `<form action={fn}>` — 제출을 함수 하나로 처리
- `useActionState` — 제출 결과와 대기 상태를 한 번에
- `useFormStatus` — 자식 버튼이 부모 폼의 제출 중 여부를 알 수 있다
- 지금은 "이런 게 있다"까지. **7단계에서 서버로 보낼 때 진가가 나옵니다**

✅ **체크포인트 3-A**: 어떤 값을 상태로 두고 어떤 값을 계산으로 둘지 스스로 판단할 수 있다.
✅ **체크포인트 3-B**: 내 상태 구조에서 위 4가지 원칙을 어긴 곳을 찾아 고칠 수 있다.

### 4단계 — 부수 효과와 커스텀 훅
**목표**: 새로고침해도 할 일이 그대로 남아 있다.

#### 4-A. 렌더링에 참여하지 않는 값 — `useRef`

- **`useRef`는 "바뀌어도 화면을 다시 그릴 필요 없는 값"을 담는 상자**
- `useState`와의 대비

  | | `useState` | `useRef` |
  |---|---|---|
  | 바꾸면 리렌더 | O | **X** |
  | 값 읽기 | 렌더 시점에 고정된 값 | `.current`로 **항상 최신** |
  | 렌더 중 읽기/쓰기 | 읽기만 | **하면 안 된다** |
  | 쓰는 곳 | 화면에 보이는 값 | 타이머 id, 이전 값 보관, DOM 참조 |

- DOM 참조: `<input ref={inputRef} />` → `inputRef.current.focus()`
- 값 보관: `setInterval` id, "이전 값"을 기억했다 비교하기
- 흔한 실수 — 화면에 보여야 할 값을 ref에 넣고 "왜 안 바뀌지" 하기

#### 4-B. `useEffect`

- `useEffect`가 실제로 하는 일 — **렌더링 결과를 외부 세계와 동기화**한다
- 의존성 배열: 없음 / `[]` / `[a, b]` 세 가지의 차이
- **정리 함수(cleanup)가 필요한 순간** — 구독, 타이머, 이벤트 리스너
- **StrictMode 이중 실행 정면돌파** (0단계에서 예고한 것)
  - 개발 모드에서 Effect가 **setup → cleanup → setup** 순으로 실행된다
  - 이걸로 깨지는 코드는 원래 cleanup이 빠져 있던 코드다. StrictMode를 끄지 말고 cleanup을 채운다
- **비동기 경쟁 조건(race condition)** — 빠르게 두 번 요청하면 늦게 온 옛 응답이 새 응답을 덮어쓴다
  - `let ignore = false` 플래그 또는 `AbortController`로 막기 (7단계에서 본격적으로)
- **`useEffect`를 쓰면 안 되는 경우** — 이 목록이 이 단계의 핵심입니다
  - props로 계산할 수 있는 값 → 그냥 렌더 중에 계산
  - 이벤트에 대한 반응(버튼 눌러서 POST) → 이벤트 핸들러에
  - 상태 A가 바뀌면 상태 B를 맞춰주는 Effect → 애초에 B가 파생 상태다 (3단계)
  - 부모에게 알리려고 쓰는 Effect → 콜백 prop으로
- 무한 렌더 루프를 **일부러 한 번 만들어 보고** 원인 설명하기
- `useLayoutEffect`는 언제 — 화면에 그려지기 **전에** 측정해야 할 때 (툴팁 위치 등). 기본은 `useEffect`

#### 4-C. localStorage와 커스텀 훅

- localStorage는 **React 상태가 아니다** — 브라우저 API, 문자열만 저장, 바꿔도 리렌더 안 된다
- 상태는 `useState`에 두고 localStorage는 **거울처럼 동기화**시키는 구조
- **lazy 초기화** `useState(() => JSON.parse(...))`
  - 괄호 안에 직접 쓰면 **매 렌더마다** 읽고 파싱한다. 초기값은 첫 렌더에만 필요한데도
  - 함수를 넘기면 첫 렌더에서 한 번만 실행된다
- 훅의 규칙: 최상위에서만 호출, 조건문/반복문 안에서 호출 금지 — **왜** 그런지(호출 순서로 상태를 찾는다)
- 로직을 `useLocalStorage`, `useTodos` 커스텀 훅으로 추출
- 커스텀 훅은 상태를 **공유하지 않는다** — 두 컴포넌트가 같은 훅을 쓰면 상태는 각각 따로 생긴다 (8단계로 이어짐)
- 탭을 두 개 열면 서로 동기화되지 않는다는 한계 확인 (`storage` 이벤트, `useSyncExternalStore`는 8단계에서 이름만)

✅ **체크포인트 4-A**: 무한 렌더 루프를 만들고 원인을 설명한 뒤 고칠 수 있다.
✅ **체크포인트 4-B**: 어떤 값을 `useState`에 두고 어떤 값을 `useRef`에 둘지 구분할 수 있다.
✅ **체크포인트 4-C**: "이 `useEffect`는 필요 없다"고 판단해 하나를 지울 수 있다.

### 5단계 — 컴포넌트 설계와 스타일링
**목표**: 앱이 "만들다 만 것" 같지 않게 보인다.

#### 5-A. 스타일링

- CSS Modules: 클래스 이름 충돌 없이 스타일 격리
- 디자인 토큰(색·간격)을 CSS 변수로 정리 — 8단계 다크모드의 밑준비
- 조건부 클래스 조합하기 (`clsx` 또는 직접 만든 함수)

#### 5-B. 합성

- `children`을 이용한 합성 — `Button`, `Card`, `Modal`
- **prop으로 JSX 넘기기** (`header`, `footer` 같은 슬롯)
- 컴파운드 컴포넌트 맛보기 (`<Tabs><Tabs.Item/></Tabs>`) — 개념만
- **"props를 몇 개까지 늘릴 것인가"** — 옵션이 늘어나면 합성으로 갈아탈 때다
- TS: `ComponentProps<'button'>`을 확장해 네이티브 속성 전부 받기

#### 5-C. ref 전달과 명령형 핸들

- **React 19부터 `ref`는 그냥 prop이다** — `function Input({ ref, ...rest })`로 바로 받는다
- `forwardRef`는 **옛 코드에서 볼 것** — React 18까지 필요했던 우회로. 읽을 줄만 알면 된다
- `useImperativeHandle` — 부모에게 `open()` / `close()` / `focus()`만 골라서 노출
  - 모달을 이걸로 만들어 보고, **대부분의 경우 그냥 props가 낫다**는 것도 같이 확인

#### 5-D. 모달과 접근성

- 삭제 확인 모달 만들기 — **포털**(`createPortal`)이 여기서 등장
  - 왜 필요한가: 부모의 `overflow: hidden` / `z-index`에 갇히지 않으려고
  - 포털로 옮겨도 **React 트리상으로는 자식** — 이벤트는 그대로 부모로 올라간다
- 열릴 때 포커스 이동, 닫힐 때 원래 자리로 복귀 (4단계 `useRef` 활용)
- Esc로 닫기, 배경 클릭으로 닫기, 포커스 트랩
- 시맨틱 태그와 `aria-*`, `<dialog>` 요소도 있다는 것

✅ **체크포인트 5-A**: 새 화면을 만들 때 기존 컴포넌트를 재사용해 조립할 수 있다.
✅ **체크포인트 5-B**: 모달을 키보드만으로 열고 닫고 조작할 수 있다.

### 6단계 — 라우팅
**목표**: 목록 / 상세 / 설정이 각각 고유 URL을 가진다.

- React Router 설치와 라우트 정의
- `Link`, `NavLink`, 중첩 라우트, `Outlet`
- URL 파라미터로 상세 페이지 만들기 (`useParams`)
- **`key`로 라우트 전환 시 상태 초기화** — 2-C에서 배운 것의 실전
  - `/todos/1`에서 `/todos/2`로 갈 때 같은 컴포넌트가 재사용되어 **입력 중이던 값이 남는다**
  - `<TodoDetail key={id} />` 한 줄로 해결
- **필터 상태를 쿼리스트링으로 옮기기** (`useSearchParams`) — URL도 상태 저장소다
  - 3단계에서 `useState`에 뒀던 필터를 URL로 이사시키기
  - 얻는 것: 새로고침 유지, 링크 공유, 뒤로가기
- 프로그래밍 방식 이동 (`useNavigate`)과 리다이렉트
- 404 페이지
- React Router의 `loader`/`action`은 다른 방식의 데이터 로딩 — 우리는 7단계에서 TanStack Query로 갑니다 (이름만 알아두기)

✅ **체크포인트 6-A**: 필터를 건 화면의 URL을 복사해 새 탭에 붙여넣으면 같은 화면이 뜬다.
✅ **체크포인트 6-B**: 상세 페이지를 옮겼을 때 이전 페이지의 입력값이 남지 않는다.

### 7단계 — 서버 연동
**목표**: 데이터가 브라우저가 아니라 서버에 저장된다.

#### 7-A. 맨손으로 해 보기

- 간단한 목 API 띄우기 (json-server 또는 MSW)
- `fetch` + `async/await`, `res.ok` 확인 (fetch는 404에도 reject하지 않는다)
- **로딩 / 에러 / 빈 상태 3종 처리** — 셋 다 화면이 있어야 한다
- `useEffect`에서 요청 보내기 + `AbortController`로 취소 (4-B의 경쟁 조건 재등장)
- **왜 이 방식이 금방 한계에 부딪히는가** — 직접 겪어 볼 목록
  - 같은 데이터를 두 화면에서 쓰면 두 번 요청한다
  - 뒤로 갔다 오면 다시 로딩 스피너
  - 데이터를 바꾼 뒤 목록을 손으로 갱신해야 한다
  - 캐시, 재시도, 중복 제거를 전부 손으로 만들게 된다

#### 7-B. TanStack Query 도입

- `useQuery` — 캐싱, 중복 제거, 배경 재요청
- **queryKey 설계** — 키가 곧 캐시의 주소다. 필터가 키에 들어가야 하는 이유
- `staleTime` vs `gcTime` — "낡았다"와 "버린다"의 차이
- `useMutation` + `invalidateQueries` — 바꾸고 나서 다시 가져오기
- **낙관적 업데이트**(optimistic update) — 성공을 가정하고 화면부터 바꾸고, 실패하면 되돌리기
- React 19의 `useOptimistic`과 비교 — 같은 아이디어의 내장 버전
- 3단계에서 맛본 `useActionState`를 여기서 async 제출에 써 보기
- 서버 데이터는 **전역 상태가 아니다** — 8단계에 들어가기 전에 이걸 확실히 해 둡니다

✅ **체크포인트 7-A**: 네트워크를 느리게 설정해도 UI가 자연스럽게 동작한다.
✅ **체크포인트 7-B**: 항목을 추가했을 때 목록이 저절로 최신이 되는 이유를 설명할 수 있다.

### 8단계 — 전역 상태
**목표**: 다크모드와 로그인 상태가 앱 전체에서 공유된다.

두 부분으로 나뉩니다. **먼저 React 내장 도구로 끝까지 밀어붙이고**, 그게 버거워지는 지점을 직접 만든 뒤에 라이브러리를 들입니다. 순서를 바꾸면 Zustand가 왜 존재하는지 영영 모른 채로 쓰게 됩니다.

#### 8-A. 먼저 Context로 해결한다

- props drilling이 실제로 아파지는 지점 체험하기 — 3단계짜리 컴포넌트를 거쳐 props를 내려보내기
- Context API + 커스텀 훅 패턴 (`useTheme`, `useAuth`)
  - Provider 밖에서 쓰면 에러를 던지게 만들기
- **Context + `useReducer` 조합** — 3-C의 reducer를 전역으로 올리기
  - 상태 Context와 dispatch Context를 **따로 두면** dispatch만 쓰는 컴포넌트는 리렌더되지 않는다
- Context를 쪼개야 하는 이유 (불필요한 리렌더)
- Provider의 `value`에 객체 리터럴을 그대로 넣으면 왜 매번 새 값이 되는지
- 로그인 여부에 따른 보호 라우트

✅ **체크포인트 8-A**: 다크모드를 토글했을 때 **어떤 컴포넌트가 왜 리렌더되는지** 짚을 수 있다.

#### 8-B. Context가 버거워지면 Zustand

- **한계 체험이 먼저**: 전역 값을 5~6개로 늘리고 Provider를 3중으로 겹쳐 보기. 값 하나가 바뀔 때 그 Context를 구독한 컴포넌트가 통째로 리렌더되는 걸 Profiler(9단계에서 다시 씀)로 확인하기
- Zustand 설치 — 스토어 하나에 **상태와 액션을 함께** 둔다
- `useStore((s) => s.theme)` — **selector로 구독 범위 좁히기**
  - Context는 **값 단위** 구독, Zustand는 **필드 단위** 구독. 이 한 줄이 8-A의 고통을 없앤다
- Provider가 없어도 되는 이유 — 스토어가 React 트리 **밖에** 살기 때문 (`useSyncExternalStore`가 다리를 놓는다)
- `ThemeContext`를 Zustand로 옮기고, `AuthContext`는 남겨 두고 **둘을 나란히 비교**하기
- `persist` 미들웨어로 4단계에서 손수 만든 `useLocalStorage`를 대체해 보기
- `useStore.getState()` — React 밖(이벤트 핸들러, 타이머, 소켓 콜백)에서 상태를 읽고 쓰는 법
- **무엇을 옮기지 않을지가 더 중요하다**
  - 서버에서 온 데이터 → TanStack Query(7단계)에 그대로 둔다. 스토어로 복사하는 순간 **사본이 둘**이 되고 어느 쪽이 최신인지 아무도 모른다
  - 필터 · 검색어 · 페이지 번호 → URL(6단계)
  - 모달 열림, 입력값, 호버 → 그냥 `useState`
  - 라이브러리를 깔았다고 상태의 대부분이 옮겨가는 게 아니다. 여전히 90%는 지역 상태다
- Jotai · Valtio · Redux Toolkit은 Zustand와 **같은 칸을 놓고 경쟁하는 대체재**다 — 하나만 고른다

✅ **체크포인트 8-B**: 앱의 상태를 **서버 / URL / 전역 스토어 / 지역** 네 칸으로 나눠 적고, 각각을 왜 거기에 뒀는지 설명할 수 있다. ([부록 B](#부록-b-상태의-네-가지-거처))

### 9단계 — 성능
**목표**: 항목 1,000개에서도 버벅이지 않는다.

#### 9-A. 먼저 측정한다

- React DevTools Profiler로 **먼저 측정하기** — 추측으로 최적화하지 않는다
- "Highlight updates" 켜고 어디가 깜빡이는지 눈으로 보기
- **리렌더가 일어나는 진짜 이유**
  - 부모가 리렌더되면 자식도 리렌더된다 (props가 안 바뀌어도)
  - 리렌더 ≠ DOM 변경. React는 대부분 DOM을 건드리지 않는다 — **리렌더 자체는 대개 싸다**
- 느린 이유가 리렌더가 아니라 **렌더당 계산량**이나 **DOM 노드 수**인 경우 구분하기

#### 9-B. 메모이제이션

- `React.memo` — props가 그대로면 리렌더 건너뛰기
- `useMemo` — 비싼 계산 결과 재사용
- `useCallback` — 함수 참조 유지 (`memo`된 자식에게 넘길 때만 의미가 있다)
- **쓰면 안 되는 경우가 더 중요하다**
  - `memo`로 감쌌는데 매번 새 객체/함수를 props로 넘기면 아무 효과가 없다
  - 싼 계산에 `useMemo`를 두르면 오히려 손해다
  - 최적화 전에 **구조를 바꿔서** 해결되는 경우가 많다 (상태를 아래로 내리기, `children`으로 넘겨서 리렌더 차단하기)

#### 9-C. 응답성 — 무거운 화면을 끊기지 않게

- **`useDeferredValue`** — 3단계의 검색어를 그대로 쓰되, 무거운 목록은 **한 박자 늦게** 갱신
  - 입력창은 즉시 반응하고 목록은 뒤따라온다
- **`useTransition`** — 이 상태 변경은 "급하지 않다"고 표시하기, `isPending`으로 로딩 표시
- 두 개의 차이: 값을 늦추느냐(`useDeferredValue`), 업데이트를 늦추느냐(`useTransition`)

#### 9-D. 그 외

- 리스트 가상화 (보이는 것만 그리기)
- 코드 스플리팅 (`lazy`, `Suspense`)

> 📌 9-B의 손으로 하는 메모이제이션은 상당 부분을 **React Compiler**가 자동으로 대신해 줍니다.
> 다만 그건 빌드 설정 이야기라 **11단계**에서 켭니다. 여기서는 컴파일러가 무슨 일을 대신해 주는 건지
> 알 수 있도록 먼저 손으로 해 봅니다. 이 단계의 측정 방법(Profiler, 렌더 시간)을 11단계에서 그대로 다시 씁니다.

✅ **체크포인트 9-A**: 최적화 전후 렌더 시간을 숫자로 비교해 보여줄 수 있다.
✅ **체크포인트 9-B**: 1,000개 목록에서 검색어를 타이핑해도 입력이 끊기지 않는다.

### 10단계 — 테스트
**목표**: 리팩터링해도 기능이 안 깨진다는 확신이 생긴다.

- Vitest + React Testing Library 세팅 (`jsdom`, `@testing-library/jest-dom`)
- **"구현이 아니라 사용자 행동을 테스트한다"**
  - 쿼리 우선순위: `getByRole` > `getByLabelText` > `getByText` > (최후) `getByTestId`
  - 상태 변수 이름이나 클래스명에 기대지 않는다
- 렌더 → 조작(`userEvent`) → 검증
- `findBy*`와 `waitFor` — 비동기 검증. `act` 경고가 뜨는 이유
- MSW로 API 목킹 (7단계에서 이미 띄웠다면 그대로 재사용)
- **커스텀 훅 테스트** — `renderHook`, `act`로 4단계의 `useTodos` 검증
- 테스트용 렌더 헬퍼 만들기 — Router / QueryClientProvider / 테마를 감싼 `renderWithProviders`
- 무엇을 테스트하지 **않을** 것인가 — 라이브러리 동작, 스타일, 구현 세부

✅ **체크포인트**: 내부 구조를 바꿔도 테스트가 그대로 통과한다.

### 11단계 — 마무리와 배포
**목표**: 남에게 보여줄 수 있는 URL이 생긴다.

#### 11-A. 프로덕션 빌드

- `vite build` / `vite preview` — 개발 서버와 무엇이 다른지
- 번들 시각화로 무엇이 무거운지 보기 (9-D의 코드 스플리팅이 실제로 먹혔는지 확인)
- 환경변수(`import.meta.env`)와 비밀값 관리
  - `VITE_` 접두사가 붙은 값은 **번들에 그대로 박혀서 브라우저에 다 노출된다**
  - API 키를 여기 넣으면 안 되는 이유. 비밀이 필요하면 서버가 필요하다

#### 11-B. React Compiler 켜기

9단계에서 손으로 하던 메모이제이션을 빌드 시점에 자동으로 넣어 주는 컴파일러입니다. **빌드 설정을 건드리는 일이라 여기서 다룹니다.**

- 무엇을 해 주는가 — `useMemo` / `useCallback` / `memo`의 상당 부분을 컴파일러가 대신 넣는다
- **왜 9단계를 먼저 손으로 했는가**
  - 컴파일러가 무슨 일을 대신해 주는지 알아야, 켠 뒤에도 남는 문제를 고칠 수 있다
  - 옛 코드와 남의 코드에는 수동 메모가 가득하다. 읽을 줄 알아야 한다
- **전제 조건 — 규칙을 지킨 코드에만 안전하다**
  - 1단계의 **컴포넌트 순수성**: 렌더 중에 바깥 값을 바꾸지 않기
  - 4단계의 **훅 규칙**: 최상위에서만 호출하기
  - 2단계의 **불변성**: 상태를 직접 수정하지 않기
  - 즉, 앞에서 배운 규칙들이 여기서 **컴파일러가 동작하기 위한 조건**으로 회수됩니다
- ESLint의 컴파일러 규칙(`eslint-plugin-react-hooks`)으로 위반한 곳 먼저 찾아 고치기
- Vite 프로젝트에 켜기 — `@vitejs/plugin-react`의 babel 설정에 컴파일러 플러그인 추가
  - 설정 방법은 버전에 따라 바뀌니 **공식 문서를 그때 확인**할 것
- 켠 뒤 **9-A의 Profiler로 전후 비교** — 숫자가 실제로 좋아졌는지
- 컴파일러가 **대신해 주지 않는 것**
  - `useTransition` / `useDeferredValue` (9-C) — 무엇이 급한지는 사람만 안다
  - 리스트 가상화, 코드 스플리팅, 네트워크 문제
- 기존 `useMemo` / `useCallback`을 지울지 — **성급히 지우지 말 것.** 켜 두고 한동안 그대로 두는 게 안전하다

#### 11-C. 에러 바운더리로 흰 화면 방지

- 렌더 중 에러가 나면 React는 트리 전체를 버린다 — 그래서 흰 화면이 된다
- React에서 에러 바운더리는 아직 **클래스 컴포넌트**다 → 실무에서는 `react-error-boundary` 사용
- **잡히지 않는 것**: 이벤트 핸들러, 비동기 코드, 서버 응답 에러
  - 그래서 7단계에서 로딩/에러 상태를 따로 처리했던 것이다. 둘은 역할이 다르다
- 라우트 단위로 두르기, "다시 시도" 버튼, 폴백 UI 설계

#### 11-D. 배포

- SPA 새로고침 404 문제 — `/todos/3`을 직접 열면 왜 404인지, `index.html` 폴백 설정
- Vercel 배포, 프리뷰 배포, 환경변수 주입
- 다음에 배울 것 정리 (Next.js, 서버 컴포넌트, 폼 라이브러리 등)

✅ **체크포인트 11-A**: React Compiler를 켜기 전후의 렌더 시간을 Profiler 숫자로 비교할 수 있다.
✅ **체크포인트 11-B**: 일부러 에러를 던져도 흰 화면 대신 폴백 UI가 뜬다.
✅ **체크포인트 11-C**: 처음부터 끝까지 혼자 새 기능을 하나 추가해 배포한다.

## 부록 B. 상태의 네 가지 거처

새 값이 생겼을 때 **위에서부터** 물어보세요. 먼저 걸리는 칸이 그 값의 집입니다.

| 질문 | 예 → 여기 | 도구 | 단계 |
|---|---|---|---|
| 1. 서버에 있는 데이터인가? | 할 일 목록, 사용자 정보 | TanStack Query | 7 |
| 2. 링크로 공유되거나 새로고침 후에도 남아야 하나? | 필터, 검색어, 페이지 번호 | URL (`useSearchParams`) | 6 |
| 3. 앱의 여러 곳에서 진짜로 함께 봐야 하나? | 테마, 로그인 여부 | Context 또는 Zustand | 8 |
| 4. 나머지 전부 | 모달 열림, 입력값, 호버 | `useState` / `useReducer` | 2 · 3 |

- 4번이 **압도적으로 많은 게 정상**입니다.
- 한 값이 두 칸에 동시에 있으면 버그입니다. **한 조각에 주인은 하나.**
- 계산으로 뽑을 수 있는 값은 어느 칸에도 두지 않습니다 (3단계 파생 상태).

## 이 커리큘럼에서 일부러 뺀 것

강의마다 다르게 가르치는 것들 — 지금 배우면 오히려 헷갈리는 것들입니다.

| 뺀 것 | 이유 |
|---|---|
| Create React App | 공식적으로 지원 종료. Vite가 표준입니다. |
| 클래스 컴포넌트 | 신규 코드에서 쓰지 않습니다. 옛 코드 읽을 때와 11단계 에러 바운더리에서만 스칩니다. |
| Redux / Redux Toolkit | 7단계(서버 상태) + 8단계(Context · Zustand)면 대부분의 앱은 충분합니다. 회사 코드에서 마주쳤을 때 배워도 늦지 않습니다. |
| Jotai / Valtio / MobX | 8단계의 Zustand와 **같은 칸**을 차지하는 대체재입니다. 전역 상태 라이브러리는 하나만 씁니다. |
| React Hook Form 등 폼 라이브러리 | 3단계에서 제어 컴포넌트를 손으로 만들어 본 뒤에 도입해야 뭘 대신해 주는지 보입니다. |
| styled-components / Tailwind | CSS Modules로 기본기를 잡은 뒤 언제든 갈아탈 수 있습니다. |
| 서버 컴포넌트 (RSC) | Next.js 같은 프레임워크가 있어야 의미가 있습니다. 11단계 이후. |
| Next.js | React 자체를 먼저. 11단계 이후 다음 목표입니다. |

## 진행 규칙

1. 레슨 문서의 코드를 **직접 타이핑**합니다. 복사해서 붙여넣더라도 한 줄씩 읽으면서.
2. 각 단계 끝의 ✅ 체크포인트를 통과하지 못하면 다음으로 넘어가지 않습니다.
3. 막히면 "왜 이렇게 되는지" 먼저 물어보고, 답을 듣기 전에 한 번 추측해 봅니다.
4. 각 단계 끝에 커밋합니다. 언제든 되돌아올 수 있게.
5. **"일부러 틀려 보기"가 들어간 항목**(무한 루프, 경쟁 조건, Context 리렌더 지옥)은 건너뛰지 않습니다. 고장 난 걸 봐야 도구가 왜 있는지 압니다.
